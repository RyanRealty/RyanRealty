## 1. Purpose

(a) A visitor on any listing page gets honest provenance without asking for it: who actually listed the property ("Listing courtesy of" + the listing participant's contact), that the data comes from Oregon Data Share, how fresh it is, and that it is deemed reliable but not guaranteed and for personal, non-commercial use (components/listing/ListingAttribution.tsx:80-113). (b) The machine outcome is that Ryan Realty's ODS IDX data license stays in good standing — which is the precondition for the listing catalog existing at all: every `find-a-home` search grid, tile, map pin, and detail page, and every capture moment that rides on them, displays licensed MLS data only for as long as these display rules are met on every render, so fully serving (a) is what keeps the machine's core inventory legally displayable.

## 2. Inception (what starts it)

Trigger: not visitor-initiated — a machine obligation that attaches the moment any surface displays ODS-licensed listing data. Two passive surfaces fire it:

1. **Every listing-detail render.** All public detail URL shapes funnel into ONE page component, so one mount covers them: `/homes-for-sale/{city}/.../{addr}-{mls}` and `/homes-for-sale/listing/{id}` rewrite to `/listing/by-address/...` and `/listing/by-key/...` (next.config.ts:292-301), and both alias pages delegate to `app/listing/[listingKey]/page.tsx` (app/listing/by-address/[...slug]/page.tsx:2-3; app/listing/by-key/[listingKey]/page.tsx:1-2,19). Legacy AgentFire URLs 308-redirect into the same component (app/listing/odsmls/[...slug]/route.ts:1-22); `/listings/:listingKey` and `/lp/listings/:listingKey` redirect likewise (next.config.ts:214,269). Entry channels for the render itself are `find-a-home`'s (organic, tiles, map pins, alerts, SMS shortlinks) — irrelevant to this process's obligation, which is per-render regardless of channel.
2. **Every page carrying site chrome.** The footer ODS caption fires site-wide, but the two registers do NOT carry identical caption sets (verified this run): SiteFooter's legal caption carries all five elements — ODS + Morgan Data Shuttle source line, reliability line, the courtesy-of-participants sentence ("All listings courtesy of participating MLS members"), license number, Equal Housing Opportunity (components/site/SiteFooter.tsx:156-163); the KB-register footer — the one the listing detail page actually mounts (app/listing/[listingKey]/page.tsx:68,575) — carries the ODS+MDS source line, reliability line, and license number (components/site/kb/KbFooter.client.tsx:141) plus Equal Housing (:126), and OMITS the courtesy sentence, which exists only at SiteFooter.tsx:158 (see §5-5 for why this is drift, not a per-listing leak). Footer coverage of every public page is itself gated (G58, scripts/check-default-chrome-footer.mjs:1-30).

Preconditions: a displayable listing row — the inception is suppressed entirely for opted-out listings (see §6): the detail DAL returns a miss → notFound() before any attribution could render (lib/data/listings/getListingDetail.ts:429-448).

A third inception is commit-time, not render-time: any commit touching the repo runs G54's static assertions inside `ci:gates` (package.json:96,230).

## 6. Decision points

- **Display vs suppress (the governing branch):** opted-out or non-IDX listing → 404 at the DAL (getListingDetail.ts:432-439) and excluded from tiles/search at the MV predicate layer (20260801053000:125-126; 20260731170000:332-333). The MV layer enforces two of the three flags; `permit_address_internet_yn` is enforced only at the detail DAL today (§10 defect 3). Live exposure verified 0 rows this run (§12 check 3).
- **Coming Soon:** never public (getListingDetail.ts:446-448; lib/listing-status-public.ts:4-9) — the no-public-Coming-Soon rule the constitution lists as precedence-ladder law.
- **Courtesy-line fallback:** office name, else agent name, else omit the line entirely — never fabricate (ListingAttribution.tsx:24-27,73).
- **Contact fallback:** office phone → agent phone → agent email (app/listing/[listingKey]/page.tsx:430), matching §5-3 P's "email OR phone the listing participant provided".
- **Sold visibility:** the shop's recorded interpretation of §5-4 A.4 is "no INDEXABLE public sold surface" (gate header :19-21) — individual history/CMA sold detail stays behind registration (page.tsx:422-425); the MV browse/search plane carries no sold rows (status array, 20260731170000:331), but the bare search page's `status=Sold` scope serves Closed rows through the legacy tile path AND is indexable today (§10 defect 10) — the recorded interpretation is currently breached by that one surface.
- **Compliance gates that bind this process:** G54 itself (`ci:ods-compliance`, package.json:96, in `ci:gates` :230); G58 footer coverage; `ci:public-listing-status` for Coming Soon. §0 data accuracy: the block's only "number" is the freshness date — currently self-referential (§10 defect 4), which is a §0-flavored honesty problem, not just a compliance one. Voice canon: the disclaimer sentences are compliance language, required verbatim by the gate's string asserts — exempt from rewriting.

## 7. Completion

- **Done-when (per render):** the listing page rendered WITH the courtesy line + participant contact + ODS logo + reliability/non-commercial disclaimers, on a listing that is licensed for display — or rendered NOT AT ALL (404) for an opted-out/non-IDX/pre-marketing listing. The footer caption rendered on the same page.
- **Done-when (per commit):** `ci:ods-compliance` green inside `ci:gates` (package.json:230).
- **Done-when (per feed cycle):** public display data no older than 12 hours (§5-3 I); the cron gives a 15-minute cadence.
- **Artifacts at completion:** the rendered block and caption (ephemeral HTML); the green gate line in the commit's `ci:gates` run. No DB write — this process only reads.
- **Terminal states:** rendered-compliant · suppressed-404 (opt-out/Coming Soon) · commit-blocked (gate red) · **silent-violation** (the failure terminal: a render missing a required element that the gate's static shape-check could not see — the state the §10 defects make possible).

## 8. Time & performance

- **Time-to-answer budget:** none of its own for the visitor — the block must not COST time: it adds zero queries (rides the existing detail select, getListingDetail.ts:128-143) and zero client JS (server-rendered, static markup). For the compliance reviewer, the answer ("is this display compliant?") must be resolvable on any single listing page + the footer — it is, by construction, when the elements render.
- **CWV reality:** this process rides `find-a-home`'s listing-detail CWV; route-level field CWV was **not queried this pass** (gap — owned by the find-a-home PDS, not re-litigated here). The block sits below the fold at the page bottom (mount :427 of a ~575-line body) and cannot affect LCP.
- **What "slow" means and who sees it:** the meaningful latency is FEED lag, not render lag — display data older than 12h is a rule breach nobody sees until an audit or an angry listing broker. The 15-minute cron cadence gives 48× headroom; the exposure is a silent wedge (delta-cursor incident class), which no render-time signal surfaces today.
