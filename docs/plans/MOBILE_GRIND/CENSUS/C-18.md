# C-18 · Geo resolution ladder (infrastructure)

`lib/data/geo/resolveGeoScope.ts` — one resolver for "what does this geography contain?", because three
geo types answer it three different ways and every caller was re-deriving it inline. That is the shared
root cause behind C-01, C-02, C-19 and C-20.

| type | membership |
|---|---|
| `neighborhood` | SPATIAL only — GIS polygon via `listings_in_boundary`. No MLS field exists for a Bend district. |
| `community` | REGISTRY — `subdivision_aliases` + `sub_neighborhoods`, or spatial via the resort boundary. **Alias-aware** (literal-name matching undercounts every resort). |
| `subdivision` | MLS `SubdivisionName`, plat polygon as fallback. |

Returns `{ type, slug, label, city, citySlug, polygon, listingPredicate, childSubdivisionSlugs,
subdivisionAliases }`. Reads route through `getGeoBoundaryMapData`; no new query is introduced.

`npm run report:geo-coverage` reads via the documented `boundary_geojson` RPC — no ad-hoc SQL.

# CORRECTION — 2026-08-06, same day

**The coverage report above is wrong, and the conclusion I drew from it was wrong.** I told Matt the
subdivision plats did not exist and that he needed to source them from Deschutes County DIAL. He already
owns them.

`boundaries` holds **3,312 rows, of which 3,213 are `geo_type='subdivision'`** — the county plat set is
already ingested.

## Why the report missed them

It asked for an exact match on `slugify(<MLS alias>)` against `geo_slug`. Recorded plat names are phased
and worded differently from MLS subdivision names, so exact match found almost nothing:

| MLS alias | recorded plats |
|---|---|
| Braeburn | `braeburn-phase-i`, `-ii`, `-iii`, `-iv` |
| Westbrook Meadows | `westbrook-meadows-p-u-d-phases-1-and-2`, `-phase-3` |
| Sunrise Village | `sunrise-village-east-knoll-section`, `-outback`, `-river-bluff`, +2 |
| Lodges at Bachelor V | `lodges-at-bachelor-view-phase-1`, `-phase-2`, `-west` |
| Campbell Road | `campbell-road-subdivision` |
| Roald West | `roald-west` |

Tetherow *itself* has **21 own-name plats** (`tetherow-phase-1..7`, `tetherow-crossing` ×8,
`tetherow-vacation-homes` ×3, `tetherow-rim`, `tetherow-cascades-vista` ×2).

**One MLS name maps to MANY recorded plats.** The C-18 census even flagged this seam as the fragile
point — and then the report was written to fail on exactly it.

## Re-measure (prefix match)

**Tetherow: 7 of 8 aliases resolve** (was reported as 1 of 8). **51 of 85 across all resorts.**

## So C-21 is NOT blocked — but do not ship the prefix rule

Prefix matching is a diagnostic, not a mapping. It is wrong in both directions:

- **Over-matches:** `Triple` → `triple-ridge-*`. This repo's own note (`KbResortOverview.tsx`) records
  that the MLS truncation "Triple" means **Triple Knot**. Triple Ridge is a different subdivision.
  Shipping that draws the wrong polygon on a real map.
- **Under-matches:** MLS abbreviations — `Bbr`, `Oww`, `DrrhTrs`, `Mtn High`, `Inn Of The 7th`,
  `1st On The Hillsites` — resolve to nothing by prefix.

The work is a **verified MLS-alias → plat-slug mapping**, checked per entry, stored in the registry
beside `subdivision_aliases`. Then the fan-out in C-21 reads that map instead of guessing.

## Lesson

A null result from a query is evidence about the query first, and about the world second. I reported
"the data does not exist" on the strength of one exact-match probe against a naming convention I had
already identified as fragile, and escalated it to Matt as a decision. The claim needed a second,
differently-shaped check before it left my mouth.
