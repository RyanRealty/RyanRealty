Ryan Realty · Admin & CRM · Ground-up rebuild

Seven decisions made the admin unusable. Not two hundred bugs.

A 12-domain, evidence-backed audit of the live admin found 24 critical and 53 high-severity defects across 252 features. They are not independent. They are the output of seven structural choices. This brief shows the reasoning: the root causes, what stays because it is genuinely solid, and the architecture those causes force. No code follows until every feature is specified against it.

01
The constraints

What has to be true here

The current admin was built like an enterprise CRM — a faithful Follow Up Boss clone — for a business that is nothing like an enterprise. Five facts about this brokerage drive every decision that follows, and the live system ignores all five.

  • It serves at most five people. Matt plus two brokers. A 150-page, 664-action surface is pure cost here — to build, to load, to navigate, to trust. The right size is small.
  • The work is a loop, not a set of pages. A lead arrives → the broker is notified → responds → sends a deliverable → tracks the outcome. The admin is organized by data source instead, so one job crosses many pages.
  • The phone is the primary surface. The "this lead wants a CMA" ping arrives in a driveway. Yet the admin is desktop-first with a thinner, lossy mobile fork — crippling the most time-critical job on the exact device where it happens.
  • Every number is a compliance artifact. Matt is a licensed principal broker. A wrong stat is a license risk, not a UX blemish — so wrong numbers must be impossible by construction, not merely fixed once.
  • Messages carry money and legal exposure. Each SMS costs money and sits under TCPA. A double-send is a compliance event. Send integrity is a hard requirement.

Root-cause analysis

The seven generators

Each block is one structural decision, the symptoms it generates (red), and — where it exists — the correct, compliance-hardened code underneath it that the rebuild keeps (green). Fixing the seven collapses the symptom classes.

RC1Data model

There is no conversation. A "thread" is just a person.

Every message is a per-person timeline row; group threads, multi-channel threads, and multiple phone numbers all collapse onto the person. There is no conversation entity at all.

group vs 1:1 indistinguishable replies silently drop participants inbox rescans 2,000 rows / 1.4 MB per click delivery receipts attach to 2 of 5 paths
RC2Interaction

No optimistic or idempotent sends; every action is a full page round-trip.

The composer is a bare form post that serially awaits Twilio plus ten DB reads plus a full re-render — no pending state, no idempotency key, and the sent text stays in the box. Mutations everywhere signal "done" by re-running the whole page.

"it hangs, I send multiple" nothing changes after tapping Send real duplicate texts to clients admin-wide perceived slowness
Keep: the suppression + quiet-hours + A2P compliance chain underneath is correct.
RC3Rendering

Desktop and mobile are two separate products, CSS-toggled.

27 mobile components duplicate the desktop trees; both are server-rendered on every request and switched by a breakpoint. They drift apart in both directions.

"behaves completely differently on mobile" CMA/BPO/newsletter absent on phone name-edit exists only on mobile double server + JS cost per route
RC4Entropy

Build-by-accretion; no single source of truth per concept.

Every feature added new routes instead of extending old ones. The residue: ~24 dead routes, 17 redirect stubs, 4 CMA build paths, 6 CMA send paths, 3 commission stores, 4 subscription models.

"bloated, duplicated, confusing" different pages, different numbers, same metric trust collapse
RC5Authorization

Access truth lives in three disagreeing places.

Nav conditionals, eight copy-pasted gate layouts, and per-page checks, none kept aligned. Server actions carry no in-body auth — the layout only gates rendering, not the POST.

6 classes of broker dead-ends unauthenticated blog/site write path → XSS unauthenticated service-role TC reads
RC6Placebo

Surfaces wired to nothing, or to the wrong source of truth.

Features that look functional but aren't wired end to end — the deepest form of "unusable," because the broker configures things that do nothing and sees numbers that are fabricated.

7 of 9 automation triggers never fire listing edits reverted by the next MLS sync "$0 team volume" from a dropped table e-sign fully built, 0 ever sent
RC7Funnel

The consumer account is severed at every seam.

Signed-in users can't reach their account from the site chrome; the save → sign-in → resume flow is broken in all three variants; the strongest buyer signal — saved homes — never reaches the CRM.

save-search / save-home "confusing" 7 parallel "homes I care about" stores response loop starved of buyer intent
Keep: the unified listing_alerts pipeline — the one healthy spine, the model for the rest.

04
Target architecture

What the constraints force

Each decision is forced by a constraint and kills a root cause. This is derived, not borrowed from a reference CRM.

kills RC1

A first-class conversation model

Conversation → participants (1..N) → typed message rows with idempotency key, provider SID, and delivery state. Group vs 1:1 becomes a property of participant count — impossible to confuse. Additive migration; the timeline stays as the activity ledger.

kills RC2

Optimistic + idempotent mutations

Send shows an instant "sending" bubble, clears the input, and carries a client idempotency key the server treats as a no-op on repeat. Actions return the changed entity and patch it in — no full-page refresh. Delivery status streams to the open conversation only.

kills RC3

One responsive tree, phone-first

Delete the mobile fork. Each surface is one component that adapts by container query, authored mobile-first for the response loop. Larger screens are progressive enhancement, not a second product. Halves server and bundle cost per route.

kills RC5

One authorization primitive

A single in-body requireAdmin(capability) guard on every action and route, and the nav is generated from the same capability map — so a shown item can never dead-end, and a mechanical gate fails the build if an action mutates without it.

kills RC6 · integrity

One metric layer, one definition

Every number resolves through one DAL function with one definition. "New leads" means one thing. A metric with no live writer is removed from the UI, never rendered as "$0." Wrong numbers become impossible, not merely corrected.

kills RC4 · RC7

One canonical surface per concept

One inbox, one composer, one CMA path, one settings home, one account menu. The 24 dead routes and placebo surfaces are deleted, not maintained. The consumer funnel shares the CRM's buyer-signal spine, so saved homes feed the response loop.

Why this is the litmus test

Every architectural decision exists to make this flow real: the conversation model so the reply context is right, the optimistic layer so it feels instant and can't double-fire, the one responsive tree so it works on the phone, the single send path so there is one obvious button, the preserved auth destination so the deep link lands. Today the same job measures 10–12 taps across 4–5 page loads with a build that can time out — and is impossible on mobile.

07
Kept core

A rebuild of surfaces, not of the engine

The compliance-critical core is correct and hard-won. Discarding it would re-introduce legal risk. The rebuild keeps the engine and replaces the interaction model, the conversation data model, the IA, and the render architecture.

  • The SMS / email compliance chain — quiet hours, suppression chokepoint (fail-closed), A2P gate, signed webhooks, forward-only delivery reconcile, merge-token refusal.
  • The AST query compiler — one buildCrmPeopleQuery with broker scope clamped inside it; the RBAC posture is consistent and correct.
  • The bulk-job framework — preflight counts, suppression estimates, chunked worker, progress poller.
  • The CMA / BPO send libs — Gmail-DWD-with-Resend-fallback, suppression fail-closed, attribution + tracking. Keep the libs, kill the redundant surfaces on top.
  • The listing_alerts pipeline — unified guest/signed-in/broker table with unsubscribe token and seen-set diffing. The model for the whole funnel.
  • The sequence-engine cron — production-grade executor with at-most-once send claims. (Its authoring UI lies about what it can do — that is RC6 — but the executor is sound.)
08
Sequencing

Risk-first, no flag-day

Specs are written for every feature regardless of order; the build rolls out in observable, individually-shippable steps.

1
Foundation — auth primitive + capability map + generated nav; the optimistic/idempotent mutation primitive; the responsive shell; drop the public-site bundle from admin.
2
Conversation model + Inbox + composer — the #1 pain, on an additive migration; the timeline stays intact.
3
Person workspace + one send path — the success flow: CMA, BPO, newsletter, saved search, phone-first.
4
Metric layer — one definition per number; delete the dead planes.
5
Transactions / TC — reconcile the three deal systems; wire or quarantine e-sign.
6
Consumer funnel — account menu, save → resume, store consolidation, intent → CRM.
7
Delete pass + gates — dead routes, redirect stubs, placebo surfaces; land the gates that prevent regrowth.
The definition of done — so placebo can't recur

A feature is not done when it renders. It is done when the round trip is proven: writer → store → reader → user-visible outcome, with a test that exercises it end to end. Every per-feature spec carries acceptance criteria of that shape. No placebo ships.
