## FIXED

### P0-1 — User-created smart lists never filtered (showed all 18,209 people)
- **Screen:** People list (`/admin/crm`) · **Repro:** apply a Stage=Pending filter →
  "New List" → save → the new `?view=N` renders ALL people, ignoring the filter.
- **Root cause:** `saveCurrentFilterAsViewAction` (`app/actions/crm-saved-views.ts`)
  wrote only the `ast` column. `listCrmPeople` + the sidebar counts (`app/actions/crm.ts`)
  read the legacy `filter` bag. A view with an empty `filter` matches everyone.
  `updateSavedViewFilterAction` already dual-wrote both — create diverged.
- **Fix:** `createSavedViewAction` accepts an optional `filter`; `saveCurrentFilterAsViewAction`
  now dual-writes `filter`+`ast` in lockstep. Verified: view 26 stored `{stage:"Pending"}`
  and the list applied it (0 of 0, matching the real Pending count of 0).
- **Commit:** b02e7c90 · **Files:** `app/actions/crm-saved-views.ts`

### P0-2 — "Create Note" silently failed for every imported contact
- **Screen:** Person detail (`/admin/console/leads/[id]`) · **Repro:** type a note →
  Create Note → textarea clears but no row is written (any contact with a `fub_legacy_id`,
  i.e. ~all 18K).
- **Root cause:** `addCrmNoteAction` (`app/actions/crm.ts`) branched on
  `person.fub_legacy_id` and called the DECOMMISSIONED FUB API (`addPersonNote`), relying on
  the (dead) mirror sync to write the local `crm_timeline` row. FUB was cut over 2026-06-24;
  that path is dead, so the note vanished. Only the never-taken `else` (no fub_legacy_id)
  wrote locally.
- **Fix:** write the local `crm_timeline` row directly for every contact; FUB branch removed;
  unused `addPersonNote` import dropped. Verified: note row 222927 written (broker=matt),
  then deleted net-zero.
- **Commit:** b02e7c90 · **Files:** `app/actions/crm.ts`

### P0-3 — Phone/email jsonb mirrors dropped `isPrimary` → wrong send target
- **Screen:** Person detail phones modal + inline email edit · **Repro:** edit phones/emails →
  the `crm_people.phones/emails` jsonb mirror is rewritten WITHOUT `isPrimary`.
- **Root cause:** `savePhoneNumbersAction` / `saveEmailRowAction`
  (`app/actions/crm-person-detail.ts`) mirrored a reduced shape (`{value,type,status}`).
  `getSendTarget` (SMS) and `sendCrmEmailAction` pick the send address by
  `.sort((a,b)=>Number(!!b.isPrimary)-Number(!!a.isPrimary))[0]` — with `isPrimary` absent the
  sort is a no-op and the FIRST stored row wins regardless of which the broker marked primary.
  A broker could text/email the wrong number after any contact-point edit.
- **Fix:** mirrors carry `isPrimary` (phones also `normalized`, matching the RETS shape the
  rest of the CRM reads). Verified round-trip: mirror now `{...,isPrimary:1,normalized}`.
- **Commit:** landed in concurrent commit 8548c0f3 (phones) + b02e7c90 confirms email path.
  **Files:** `app/actions/crm-person-detail.ts`

### P1-4 — Email Templates list had no delete affordance
- **Screen:** Templates (`/admin/crm/settings/templates`) · **Repro:** an email template row's
  Actions column shows only a pencil — no trash. Text Templates had both. Spec §13 (rows 29,
  152, 189, 651–656) requires a Trash icon + confirmation `<AlertDialog>` on BOTH.
- **Fix:** added the same superuser-only, `usage>0`-guarded `Trash2` button + delete
  `AlertDialog` to `EmailTemplateList` (wired to the existing `remove` action, which already
  refuses templates referenced by a live automation). Verified: created "ZZ Audit Template"
  (row 115) → deleted via the new trash + confirm → gone from DB and UI.
- **Commit:** 90ced1de · **Files:** `components/admin/crm/settings/templates/EmailTemplateList.tsx`

### P1-5 — Contact Attempts report missing Marketing + Deals sub-tabs
- **Screen:** Reporting → Contact Attempts (`/admin/crm/reporting/contact-attempts`) ·
  **Repro:** its tab strip has 10 tabs; every other report page has the full 13 (adds
  Marketing + Deals). A broker on Contact Attempts had no in-strip route to those reports.
- **Root cause:** each report page hard-codes its own `REPORTING_TABS` array; the
  contact-attempts copy predated the Marketing/Deals additions.
- **Fix:** added Marketing + Deals to the contact-attempts strip.
- **Commit:** 90ced1de · **Files:** `app/admin/(protected)/crm/reporting/contact-attempts/page.tsx`
- **Note (P2-9 below):** the 13× duplicated `REPORTING_TABS` array is the reason this drifted;
  a shared constant would prevent recurrence.

### P1-6 — Agent Goals "Set goal" link 404'd
- **Screen:** Reporting → Agent Goals (`/admin/crm/reporting/agent-goals`) · **Repro:** click
  "Set goal" on any agent row → navigates to `/admin/crm/reporting/agent-goals/set-goal?...`
  which does not exist → 404 page.
- **Root cause:** the link pointed at a "future settings route" that was never built.
  Commission-goal persistence is a documented V1 deferral (`getAgentGoalsReport.ts`:
  `commissionGoal` hardcoded null, "no crm_goals table exists").
- **Fix (graceful degradation, no fabricated feature):** replaced the dead link with a muted
  "Not set" placeholder (`title="Commission goal-setting is coming soon."`) and updated the
  banner copy to state goal-setting is a future increment while the live columns (closed/
  upcoming deals, commission earned) still render. No dead navigation.
- **Commit:** 90ced1de · **Files:** `app/admin/(protected)/crm/reporting/agent-goals/page.tsx`

## OPEN (P2 — coherence/polish, non-blocking)

### P2-7 — Reporting hub/overview H1 is 20px; every other CRM screen's H1 is 24px
- `/admin/crm/reporting` + `/reporting/overview` render the page title at 20px; Automations,
  Templates, Company, Tasks all use 24px. Minor visual inconsistency, not a broken feature.
- **Suggested fix:** normalize the reporting page H1 to the 24px CRM page-title size.

### P2-8 — 13× duplicated `REPORTING_TABS` array (the cause of P1-5)
- Every `reporting/*/page.tsx` re-declares the tab strip inline. This is why Contact Attempts
  drifted out of sync (and how a future tab add could miss pages again). Extract one shared
  `REPORTING_TABS` constant (with a per-page `active` marker) so the strip cannot diverge.

### P2-9 — CRM page headers use GeistSans, not the Amboqia display face
- CLAUDE.md's design rule wants page H1s/H2s in Amboqia on the public site. The CRM admin
  surface uses GeistSans headers throughout — but it does so CONSISTENTLY across all 10
  screens and it matches the FUB-parity product-surface target (FUB uses a sans headline).
  Logged for a Matt call: keep sans (product-surface, my read) or migrate CRM titles to the
  display face for brand consistency. Not treated as a defect because it is internally coherent.

## COHERENCE VERDICT

The 10 desktop screens read as ONE CRM. Shared top nav (Dashboard·CRM·Deals·Reports·Admin +
command palette) is byte-identical everywhere; navy `#102742` primary + cream tokens are used
consistently; every screen builds from `@/components/ui/`; page titles share the GeistSans 24px
idiom (one 20px outlier on Reporting, P2-7); table/toolbar/empty-state idioms and the FUB date
convention ("Last communication Jun 1", "6 months ago") are consistent. No screen "looks like a
different CRM." The only coherence nits are the reporting H1 size, the duplicated tab arrays, and
the sans-vs-Amboqia header question — all P2, none blocking.
